## Findings -> Actions

### 1) Benchmark lacked multi-round stability and deterministic data

Problem:
- Single-run metrics are noisy and hard to compare across runners.
- Fixture generation was not deterministic enough for cross-machine comparison.

Actions:
- Enhanced `benchmarks/benchmark_import_service.py` with:
  - `--rounds` for multi-round execution
  - `--warmup` rounds excluded from summary
  - `--seed` for deterministic fixture generation
- Added summary metrics: median + p95 for validate/preview/commit/total.

Acceptance:
- Benchmark output now contains stable `summary` and per-round `runs` sections.
- Warmup does not affect final statistics.

### 2) No automated regression gate against historical baseline

Problem:
- CI had no objective performance regression check.

Actions:
- Added baseline compare options in benchmark script:
  - `--baseline-json`
  - `--regression-threshold`
  - `--fail-on-regression`
  - `--export-json`
- Implemented comparison payload with metric deltas + regression list.
- Added `.github/workflows/performance-gate.yml` for PR/per-dispatch gate.
- Added `.perf` policy in `.gitignore`:
  - ignore all artifacts under `.perf/*`
  - keep `.perf/baseline.json` tracked.

Acceptance:
- Benchmark exits non-zero when regression exceeds threshold.
- CI workflow can fail PR based on baseline comparison.

### 3) Service-level observability needed explicit lifecycle events

Problem:
- Import lifecycle had no unified event emission contract.

Actions:
- Added optional `event_hook` in `ImportExportService` constructor.
- Added structured event emitter `_emit_event` and lifecycle events for:
  - `upload_parse_validate.started/completed/failed`
  - `preview.started/completed/failed`
  - `commit.started/completed/failed`
- Defined `ServiceEventHook` protocol in `service_types.py`.
- Added/updated observability tests in `tests/test_service.py`.

Acceptance:
- Hook receives structured events with stable event names.
- Hook errors are swallowed and do not break business flow.

### 4) Overwrite/error contract consistency required matrix coverage

Problem:
- Overwrite behavior and error-type contract needed stronger regression safety.

Actions:
- Added overwrite matrix tests for:
  - easy layer (`tests/test_easy.py`)
  - SQLAlchemy/SQLModel/Tortoise contrib adapters
  - integration lifecycle matrix (`tests/test_integration.py`)
- Ensured overwrite priority remains:
  1. `overwrite_mode`
  2. `allow_overwrite` fallback
- Aligned docs to unified error contract (`schema_error/type_error/db_conflict`).

Acceptance:
- Overwrite propagation to validate/persist handlers is verified by tests.
- Contract terminology is consistent across API and docs.

### 5) Docs and release metadata were out of sync with implementation

Problem:
- Skill/docs/changelog did not fully reflect latest capabilities.
- RTD and tag-release usage needed clearer operational guidance.

Actions:
- Reworked key docs pages and skill sheet:
  - `.github/skills/fastapi-import-export/SKILL.md`
  - `docs/api.rst`
  - `docs/getting_started.rst`
  - `docs/contracts.rst`
  - `docs/observability.rst`
  - `docs/performance.rst`
- Updated `CHANGELOG.md` (Unreleased section).
- Fixed `docs/api.rst` code-block indentation.
- Clarified performance threshold note to match workflow example (`0.30`).

Acceptance:
- Core docs are aligned with current API/behavior.
- RTD source docs are ready for push-based build.

## Risks and Mitigations

- Risk: CI runner noise causes false positive regressions.
  - Mitigation: use warmup + multiple rounds + practical threshold (e.g. `0.30` on shared runner).
- Risk: docs drift after future API changes.
  - Mitigation: update `SKILL.md`, `docs/*.rst`, and `CHANGELOG.md` in same PR.
- Risk: RTD build succeeds but wrong version visibility.
  - Mitigation: activate target tag in RTD `Versions` and keep `latest/stable` mapping explicit.
